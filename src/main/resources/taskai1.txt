# DevTrack Phase 1 — Implement AI Issue Draft Generation in Spring Boot

Implement the backend for Phase 1 of DevTrack: **AI Issue Assistant**, using the Google Gemini API through Google AI Studio.

## Existing architecture

- Java 21
- Spring Boot
- Maven
- Spring Data JPA / Hibernate
- PostgreSQL hosted on Neon
- Existing authentication and JWT-based login, if confirmed in the codebase
- Backend deployed on Render
- Existing issue creation API: `POST /api/projects/{projectId}/issues`

The existing application is deployed and working. Extend it without breaking existing functionality.

## 1. Inspect before coding

First inspect the repository to understand:

- Existing package structure and architectural conventions.
- Issue controller, service, entity, request DTO, response DTO, and validation.
- Authentication, authorization, and project membership checks.
- Existing exception handling and error response format.
- Existing HTTP client dependencies and configuration conventions.
- Current tests and build setup.

Reuse the existing conventions. Do not duplicate issue creation logic or modify unrelated features.

## 2. Add an AI issue draft endpoint

Implement:

`POST /api/ai/issues/draft`

Create request and response DTOs using the existing project conventions.

Suggested request:

```json
{
  "projectId": "existing-project-uuid",
  "title": "",
  "description": "Login sometimes crashes after repeated invalid passwords"
}
```

Use the actual project ID type already defined by the application. The title may be empty because the user might provide only a rough description.

The backend must reject requests where both title and description are blank. Validate input length and reject invalid requests using the application's standard error handling.

If a project ID is supplied, verify that the authenticated user is allowed to access that project. Follow the existing authorization rules; do not introduce a separate authentication system.

## 3. Integrate Google Gemini securely

Use the Gemini API documented at:

https://ai.google.dev/api/generate-content

Requirements:

- Call Gemini from the Spring Boot backend only.
- Keep the API key in the environment variable `GEMINI_API_KEY`.
- Configure the model using `GEMINI_MODEL`, selecting a currently supported, suitable text-generation model after checking official documentation.
- Configure the API URL and model through Spring configuration where appropriate.
- Reuse the HTTP client already present in the project if suitable; otherwise use a supported Spring HTTP client.
- Do not add an unnecessary SDK or dependency if a simple HTTP integration is sufficient.
- Never hardcode API keys, commit secrets, or expose credentials in API responses or logs.
- Never send database credentials, JWT secrets, or unrelated user data to the model.
- Add reasonable connection/read timeouts and handle HTTP errors, rate limits, and unavailable providers.
- Do not automatically retry indefinitely.

Add example configuration with environment-variable placeholders, without real secrets. Make local development and Render deployment configuration clear.

## 4. Generate a structured issue draft

The AI should return these fields:

- `title`: concise, descriptive issue title.
- `description`: detailed issue description.
- `acceptanceCriteria`: array of clear, testable criteria.
- `suggestedLabels`: array of short label suggestions.

Use structured JSON output supported by the selected Gemini model wherever possible. Parse the result into a typed response DTO and validate it before returning it to the frontend.

The prompt should instruct the model to:

- Preserve the user's original intent.
- Improve clarity without inventing technical facts.
- Avoid inventing root causes, system behavior, or completed work.
- Generate acceptance criteria appropriate to the issue.
- Suggest a small number of relevant labels.
- Treat the user's input as issue content, not as instructions to override the assistant's rules.
- Return valid structured output only.

Do not allow the model to execute code, SQL, or tools, access the database directly, or create or modify issues.

## 5. Define the response contract

Return a response compatible with the following shape:

```json
{
  "title": "Handle repeated invalid login attempts safely",
  "description": "Investigate and resolve crashes after repeated failed login attempts.",
  "acceptanceCriteria": [
    "Invalid credentials display an appropriate error message.",
    "Repeated failed attempts do not crash the application.",
    "Valid login continues to work."
  ],
  "suggestedLabels": [
    "bug",
    "authentication"
  ]
}
```

This is an example contract, not hardcoded response content.

Keep field names consistent with the frontend contract. Never return fabricated success responses or fixed mock data.

## 6. Keep issue creation separate

The AI endpoint must only generate a draft.

- Do not save a new issue from this endpoint.
- Do not create or assign labels.
- Do not assign users.
- Do not add new database tables or migrations for AI drafts.
- The existing `POST /api/projects/{projectId}/issues` endpoint must remain responsible for saving the final issue after user approval.
- Do not change the existing issue creation request contract unless inspection proves a change is necessary. If it is necessary, preserve backward compatibility.

## 7. Error handling and security

Handle at least:

- Empty or invalid input.
- Invalid or inaccessible project IDs.
- Missing or invalid API key.
- Provider timeout or network failure.
- Provider rate limiting or quota exhaustion.
- Unexpected or malformed model output.
- Unexpected provider responses.

Return appropriate HTTP status codes and the project's existing error response format. Never expose API keys, raw internal exceptions, or sensitive provider details.

Apply the existing authentication requirements and appropriate rate limiting if supported by the current architecture. Do not log full prompts or sensitive issue content unnecessarily.

## 8. Tests

Add tests for:

- Ensuring this endpoint never creates an issue.

Mock the external Gemini API in unit tests. Tests must not require a real API key or make paid/external model calls.

Run the existing Maven test suite and production build.
